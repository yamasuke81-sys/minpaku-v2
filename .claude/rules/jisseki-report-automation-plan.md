# 事業実績報告（住宅宿泊事業法14条 定期報告）自動化 — 進行計画（複数セッション継続用SSOT）

`.claude/rules/` 配下なので毎セッション自動ロードされる。**チェックポイントごとに更新する**。

## ゴール
偶数月1日に自動発火 → v2の実績を集計 → 民泊制度運営システム用CSVを生成 → Discordで数字を提示 → やますけが「✅登録する」を1回押すだけでアップロード・登録完了。期限15日まで未完了なら毎朝催促。

## 制度・システム仕様（2026-08-10 に公式PDFで確定）
- **報告期限 = 2,4,6,8,10,12月の15日まで、その前2ヶ月分**（施行規則第12条2項）。例: 6・7月分→8/15、8・9月分→10/15
- **下書き保存は存在しない**。『事業実績報告登録』画面は「保存」を押した瞬間に登録完了（確認画面なし）
- **修正は報告期間の翌月15日まで可能**（例: 8-9月分は11/15まで）。ただし同一物件で別事業者の報告期間と被る場合は不可。期間外は行政担当者に連絡
- **宿泊実績0でも報告義務あり**（届出済みなら。0を入力して保存）
- 報告方法は2通り: ①『事業実績報告登録』画面で入力 ②**CSVアップロード**（『事業実績アップロード』画面）
- 報告事項の定義（定期報告に係る留意事項）:
  - **宿泊日数** = 人を宿泊させた日数。例「6/20 17時IN → 6/24 10時OUT = 4日」＝**宿泊日のユニーク集合の要素数**
  - **宿泊者数** = 実人数の合計。同一人物の連続宿泊は1人、分割宿泊はそれぞれ1人
  - **延べ宿泊者数** = 各日の全宿泊者数の合計 ＝ Σ(人数 × 泊数)
  - **国籍別内訳** の合計＝宿泊者数（画面が自動計算で連動するため、日本人も「日本」列に入れる）

## 実機で確定した仕様（2026-08-10 debug Chrome で実測）
システムは **Salesforce Visualforce**。リンクは `href="#"` のJS遷移＋ViewState方式なので、URL直打ちではなく**クリックで辿る**必要がある（一覧・詳細ページはIDのURL直打ち可）。セッションタイムアウトのダイアログ（「続けて使用する」）あり。

| 画面 | URL / 操作 |
|---|---|
| ホーム | `https://www.minpaku.mlit.go.jp/jigyo/` |
| 事業実績一覧 | `https://www.minpaku.mlit.go.jp/jigyo/jissekilist`（ホームから「事業実績一覧」クリックで到達） |
| 事業実績報告 詳細 | `https://www.minpaku.mlit.go.jp/jigyo/{recordId}` |
| **CSVアップロード** | `https://www.minpaku.mlit.go.jp/jigyo/jissekicsv`（ホームから「事業実績アップロード」クリック） |

**CSVアップロード画面の構造（自動化の本命）**
- `input[type=file][name="attFile"]#JissekiCsvInput` … Playwright の `setInputFiles` で投入可
- `input[type=submit][value="登録"]` … これを押すと登録確定
- 結果表示: 「以下の届出の実績を登録しました。 **正常件数：N 異常件数：N 異常理由**」 ← ここを読んで成否判定する

**『事業実績報告』のフィールドID（詳細/登録/修正で共通）**
- `Jisseki_TodokedeNumber__c` 届出番号 / `Jisseki_Name` 報告期間
- `Jisseki_AccommodationDate__c` … **hidden。宿泊日をセミコロン区切りで保持**（例 `2026-06-01;2026-06-02;2026-06-06;…`）。カレンダーのクリックはこの hidden を書き換えているだけ
- `Jisseki_SyukuhakuNissuu__c` 宿泊日数 / `Jisseki_SummaryCount` 宿泊者数 / `Jisseki_Summary__c` 延べ人数
- 国籍22（この順）: `Jisseki_GuestOf` + `Japan / Korea / Taiwan / HongKong / China / Thai / Singapore / Malaysia / Indonesia / Philippines / Vietnam / India / UK / German / France / Italia / Spain / Russia / USA / Canada / Australia / Others` + `__c`
- 修正可能期間内は詳細画面に `変更` submit ボタンが出る

**報告期間の表記（実機の実データ）**: `2026年度06月～07月`（月は2桁ゼロ埋め・`～`は全角波ダッシュ）。年度＝会計年度なので **2026年2月・3月分は「2025年度02月～03月」**。次回は **`2026年度08月～09月`**

**届出番号**: the Terrace 長浜 = **第M340055098号**

**送信済み実績の履歴**（2026-08-10時点で一覧にあるもの）: 2025年度08月～09月 / 10月～11月 / 12月～01月 / 02月～03月 / 2026年度04月～05月 / **2026年度06月～07月**

## CSVフォーマット — 実機アップロードで検証済み（2026-08-10）
存在しない届出番号のみを含むCSVを実際に投入して確認（**正常件数0＝実績は1件も登録されていない**）。

- **文字コード = Shift_JIS(cp932)・BOMなし・改行CRLF**。
  **UTF-8 BOM付きは不可** — 先頭セルが `\ufeff届出番号` になりヘッダーと認識されず、1行目がデータ扱いされて全項目エラーになる（＝**システムはヘッダー行を文字列一致で判定している**）
- **1行目ヘッダー（この28列・この順序）**:
  `届出番号,報告期間,宿泊日数,宿泊者数,宿泊延べ人数,日本,韓国,台湾,香港,中国,タイ,シンガポール,マレーシア,インドネシア,フィリピン,ベトナム,インド,英国,ドイツ,フランス,イタリア,スペイン,ロシア,米国,カナダ,オーストラリア,その他,宿泊日`
- **届出番号**: `第M340055098号` の形式で**正しいと実証済み**（実在番号にしたら「届出番号が無効です」が消えた）
- **報告期間**: `2026年度06月～07月`（波ダッシュは U+FF5E）。**届出ごとの有効な報告期間と照合される**（存在しない `9999年度…` は「報告期間が無効です。（フォーマット不備）」になる）。無効な届出番号を渡すと報告期間側にも連鎖してエラーが出るので、エラー文面だけで原因を判断しない
- **宿泊日**: `2026-06-01;2026-06-02` のセミコロン区切り。**検証通過済み**
- 宿泊日数・宿泊者数・宿泊延べ人数・国籍22列も**すべて検証通過済み**（数値のみ）
- 「登録」押下時に **confirm ダイアログ**「登録しますか？※登録後は修正する事はできません。」→ OKで確定（自動化ではここを承認する）
- 結果画面: 「正常件数：N／異常件数：N」＋異常理由テーブル（届出番号・報告期間・エラー内容）。
  **エラー時は1件も登録されない**ので、形式ミスがあっても事故にならない（＝安全側に倒れる設計）
- ※confirmは「修正できません」と警告するが、実際は詳細画面に `変更` ボタンが出る期間（報告期間の翌月15日まで）は修正可能

**検証スクリプト**: `scratchpad/portal-inspect.mjs`（画面構造の読み取り専用）/ `portal-csv-test.mjs`（CSV投入＋結果読み取り）。playwright-core は ESM から絶対パスで読む（`file:///C:/Users/yamas/.claude/scripts/node_modules/playwright-core/index.js`、NODE_PATHはESMでは効かない）

## 実装方針
- **CSVアップロード方式を主軸**。画面入力は宿泊日をカレンダーで1日ずつクリックする必要があり脆い
- 集計は**サーバ側（Cloud Functions）に一本化**し、画面とCSVが必ず同じ数字になるようにする（教訓: 内訳と総数を別ロジックで出さない）
- ポータルへの操作は既存の常駐 debug Chrome（CDP:9222）のログイン済みセッションを使う。**パスワード入力は自動化しない**。セッション切れは🔑ボタンで再ログイン誘導（ドコモ光・Booking.com と同型）

### この突合で確定したコードのバグ（サーバ側集計で必ず直す）
1. **`calcNightsInMonth` のタイムゾーン混在**: `new Date("2026-07-01")` はUTC、`new Date(y, m-1, 1)` はローカル(JST)。**月をまたぐ予約が1泊多く出る**（ZHANG 6/27→7/1 は4泊なのに nights1+nights2=5）。合計(`totalNights`)は正しいので報告値には出ないが、月別内訳が狂う。日付は文字列のまま比較するか、UTC基準に統一する
2. **国籍変換表に主要な表記が無い**: `KOREA`(大文字)は `korea` 小文字化で拾えるが、**`SWEDEN` のように22区分に無い国は「その他」が正**。変換表を強化しつつ、**「その他」に落ちた人は国名をDiscordに明記して報告**する（やますけ決定 2026-08-10）
3. 宿泊日・延べ人数の**報告期間クリップ**は今回のデータでは差が出なかった（期間境界をまたぐ予約が無かった）が、一般には必要。ただし1の修正が前提
